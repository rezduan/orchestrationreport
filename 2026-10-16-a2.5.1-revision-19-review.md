## 2. Findings

### R19-01: HIGH. The survival key is asymmetric; text → binary (and from-absent opaque additions) still drop out of relevance, giving a false MERGED and a false CV3

**Section:** §1.7.3 "Survival key", rule (ii); §1.7.4 superseded, B; §11.61 row "text → binary, binary → binary, symlink/gitlink changes | content | superseded (unchanged: C's object was replaced)"; "Why a surviving change cannot drop out".

**Quoted evidence:**
- §1.7.3: sk = "kind(X,p) when kind(Post,p) = tree …, or when kind(Post,p) = text and kind(Pre,p) is non-textual … — the identity of the resulting text or directory may change on the branch later without C's change ceasing to exist; content(X,p) otherwise (C's post-state is a binary, symlink or gitlink, or absent)."
- (iii) fires only if "entry(Pre,p) ≠ ⊥, entry(Post,p) ≠ ⊥, mode(Post,p) ≠ mode(Pre,p)".

**Counterexample.** This is the exact mirror of FX-K31t, ancestry-merge, interim (a) × B.
- **F0:** p is a text file (100644, t0); g is a text file.
- **Branch br:**
  - C replaces p with a binary (100644, v0) and adds line Lg to g.
  - A later branch commit D edits the binary: End(p) = (100644, v1).
- **Target:** Hr edits p's text, giving (100644, t3).
- **Merge:** P = `merge --no-ff` (Hr, X). p conflicts (binary versus text) and is resolved to Hr's t3. g merges cleanly.

Derivation:
- **p:**
  - Pre is textual and Post is binary, so p is C-opaque.
  - kind(Post) = binary, so sk = content.
  - content(End) = (binary, v1) ≠ (binary, v0) = content(Post), so (ii) fails.
  - Both modes are 100644, so (iii) does not fire. (i) and (iv) apply only to C-text paths.
  - p is therefore **not relevant**, and superseded = 1.
- **g:** relevant, and r = e, so it is landed.
- **Anchoring:** Bu = F0 = Ht ⊑ Pre, so it is trivially true.
- **PR:** entry(Hr, p) = entry(P, p) = t3, so PR = 0. There are no revert events.
- **Content:** K = k = 1 and b = B = 0, so content state 3 is sufficient.
- **Result:** **MERGED K23, CV1, CV3, CV6.** CV3 says "1 of this commit's changes were replaced on its own branch".

This is false in the same sense the R18 review found for FX-K31t. C's conversion of p from text to binary still holds at the branch end: End is a binary, and every text line of Pre is gone. But the integrated state holds the target's text file, which descends from Pre. C's change at p is entirely absent from Tip, and nothing checks it. If C had instead deleted all of p's text lines (a C-text change), rule (i) would keep p relevant (S_R > 0) and the result would be K31. So the false MERGED depends only on whether C's result is a binary.

**Further members of the class** (uncertainty: low; each follows mechanically from the definitions):
- **(b) absent → binary, symlink or gitlink, then a later branch edit.** Pre is ⊥, so (iii) cannot fire. sk = content, the content differs, so the path is superseded. Example: the target independently adds a text p, and the add/add conflict is resolved to the target's version. Result: MERGED + CV3, while C's addition still exists on the branch and is absent from Tip.
- **(c) Opaque deletion, then a re-add on the branch.** Pre is binary v0. C deletes p; sk = content(⊥). D re-adds p as a text file. The target modifies the binary, and the resolution keeps the target's binary. sk(End) = (text, …) ≠ ⊥, so the path is superseded and the result is MERGED. By contrast, the C-text analogue (C deletes a text file, D re-creates it with different lines) stays relevant under (i), because S_R > 0.

**Why (iii) hides the gap.** text → symlink and text → gitlink stay relevant only because the git mode changes (100644 → 120000/160000), which makes (iii) fire. FX-K31u's note concedes this. text ↔ binary keeps 100644/100755, so nothing catches it. The §11.61 row "symlink/gitlink changes … superseded (unchanged)" is wrong for text → symlink/gitlink; see R19-03.

**Impact.** A false MERGED (the outcome stays reachable) and a false CV3 in the rule in force. This is the fourth repair in the relevance family (R12-01, R17-01, R18-01), and the universal claim in "Why a surviving change cannot drop out" is still not true.

**Smallest correction.** Separate "must land" from "counts as surviving content":
- **Relevance (ii′):** p is C-opaque, content(Post,p) ≠ content(Pre,p), and **content(End,p) ≠ content(Pre,p)**. In words, the branch end still differs from C's parent at p. This is the rule the author offered in residual (z). It is a superset of the sk rule, so it only makes landing stricter. It closes (a), (b) and (c), and it still excludes a branch-side restore of Pre (genuinely undone).
- **Keep sk for B, b and superseded.** Using End ≠ Pre for B would turn some K21 results into MERGED. Example: binary v0 → v1 by C, v1 → v2 by D, landed: C's bytes are not in Tip, but under End ≠ Pre this would count as surviving content.
- Add a FX-K31t-mirror fixture (text → binary + edit + overwrite → K31) and fixtures for (b) and (c).
- Extend L-27 to cover the new cost.

At minimum, sk = kind whenever kind(Pre) ≠ kind(Post) closes (a) and (b). It does not close (c).

### R19-02: MEDIUM. CV1 items (1)–(4) are still not exactly rules (i)–(iv)

**Section:** §1.10 CV1; §11.62 ("CV1 neither over- nor under-claims"); PV-28. Under (a), §1.10 says "the covered files are exactly AS".

**Mismatches:**

1. **Item (1) says "is still text at the branch end"; rule (i) says "End is textual at p", which includes absent.**
   - Counterexample: C removes line L from f, and a later branch commit deletes f. End(L) = 0, so S_R = 1, L is touched, and f is relevant by (i) and in AS. CV1 says f is not covered ("no other file is covered").
2. **Item (2) says "text both before and after this commit … (… or an empty file)"; rule (iv) includes adding or deleting an empty or whitespace-only file, where Pre or Post is absent.**
   - The item contradicts itself: an added empty file was not text before.
   - FX-K20d's kind of path, when it appears beside a counted change, is relevant but not covered.
3. **Item (3)'s sub-clauses cover only "a binary, symlink or submodule result" and "a text file or directory that replaced a non-text object".**
   - **text → directory:** sk = kind for any tree result. In FX-K23ao and FX-K31r, d was text before. The directory replaced a text object, not a non-text one, so neither sub-clause applies, yet d is relevant.
   - **Opaque deletion (Post absent):** relevant by (ii) when End is absent (FX-K23ak's bin2), but no sub-clause names an absent result.
4. **Item (4) says "permission bits"; rule (iii) compares the whole git mode, which includes 120000, 160000 and 040000.**
   - FX-K31u and FX-K31w state that (iii) fires for symlink → text and directory → file.
   - A text → symlink path retargeted later is relevant only by (iii), and CV1 does not cover it.

**Impact.** Every mismatch is an under-claim. Clause A stays true on the subset CV1 names, so there is no false-safety statement. But "no other file is covered" is false for these files, and the exactness claim of §11.62 and PV-28 (the R18-02 resolution) does not hold. If the owner later rewords CV1 to "the covered files" as a set, the gap could become an over-claim.

**Smallest correction.** In the CV1 text:
- (1): "is still text, or absent, at the branch end";
- (2): "text or absent before and after";
- (3): "for a directory result, still a directory" and "for a deleted object, still absent"; with R19-01's (ii′), state "still different from before this commit";
- (4): "whose file mode (including a change of type such as file ↔ symlink) …".

Then re-check FX-K23ao, FX-K23ak and K20d-type paths against the new text.

### R19-05: LOW. The start of the repeated-calls sequence is under-specified

**Section:** §1.7.3, "Repeated calls (… the sequence includes IA1–IA6 before FINALIZE)".

**Evidence:** decide() issues argvs before IA1 that recur later:
- NB = `merge-base --all C T` is identical to the endpoint check's argv for X = C ∈ E;
- the K04 check's paths(C) `diff-tree` is identical to the paths(C) read by relevance, PR and CK.

The rule says an injection "fails at the first occurrence … in the sequence, and only there". If the sequence starts at IA1, the rule names the endpoint check, but in time the call fails earlier, at NB. Every case examined still ends in C10, so the outcome is unaffected. The text is internally inconsistent all the same.

**Smallest correction:** "the sequence is every git call issued by decide() after phase C, in issue order".

### R19-06: LOW. The 8 MiB blob limit has an undisclosed fail-closed cost

**Section:** §1.7.3 kind rule ("NUL in its first 8000 bytes"); read discipline; §1.12.

**Evidence:** kind needs a blob read for every regular file in Pre, Post and End (relevance) and, for C-text paths, in all six CK states. A blob over 8 MiB gives C08. So any C that touches a binary over 8 MiB (PDFs, images, archives) is a TOOL_FAILURE, even though kind needs only the first 8000 bytes. The §1.13 limitations list does not mention this.

**Smallest correction:** add an L-entry, or state it under P-19 so the owner sees it.
