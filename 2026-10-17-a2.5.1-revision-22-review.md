## 2. Findings

### R22-01 — MEDIUM — CV3 attributes count-level losses to "this commit's changes"
**Where:** §1.10 CV3; §1.7.4 superseded; §11.85's table "CV3 checked against every source of superseded".

**Evidence:**
- CV3 reads: "<superseded> of this commit's changes (counted per line copy …) were changed again on its own branch … — edited, replaced, removed, undone, or deleted and re-added; part of such a change may still be present."
- §11.85 marks "A − S_A … removed … yes" and "R − S_R … re-added … yes ('undone')".
- L-4 says: "Identical text lines cannot be told apart."

**Counterexample (additions):**
- Squash. Pre f = "L\nA\n". C appends L, so Post = "L\nA\nL\n" and A(L) = 1. C also adds Lg to g.
- A later branch commit deletes the *first* (pre-existing) L. End f = "A\nL\n", so End(L) = 1 = Pre(L), S_A = 0 and superseded = 1.
- The target is untouched, so both paths land with r = e. g gives K = k = 1, state 3.
- Result: MERGED + CV1, CV3, CV6. CV3 says one of C's changes "was removed", but C's line is fully present and the branch removed a different copy.

**Counterexample (removals):** C removes one `}`. A later branch commit adds an unrelated function containing `}`. Now R − S_R = 1, and CV3 says C's removal was "undone". Common lines (`}`, `</div>`, `@endif`) make this frequent.

**Impact:** a caveat on a MERGED line states as fact something the counts cannot show. This is the same kind of defect as R21-01 ("replaced"). "Part … may still be present" does not cure it, because the sentence still asserts that C's change was changed again.

**Smallest correction:** reword the CV3 PDB, for example: "By net line counts per file (and per non-text file), <superseded> of this commit's changes no longer appear at the branch end as this commit left them; the branch changed the file after this commit, but which copy was affected is not established, and part or all of such a change may still be present." Then:
- update §1.7.4's sentence that superseded counts "only changes … changed again";
- update the §11.85 table rows for A − S_A and R − S_R;
- extend PV-33 (4) to cover this.

### R22-02 — MEDIUM — the Revision 21 movement toward MERGED is under-disclosed (FX-K23ay class)
**Where:** header "Outcome movements disclosed"; §11.87 "Exact condition"; residuals (j) and (ff); §11.77 table.

**Evidence:**

- Residual (ff) says the container case "is the instance where C's line may still exist and is unchecked".

**Counterexample 1:** FX-K23ay. End is textual, f has no S(i), and a later target commit makes f binary.

**Impact:** R21-03, a disclosure finding, is not fully resolved. The owner sees a narrower loosening than the one that occurred.

**Smallest correction:**

### R22-03 — MEDIUM — per-run sequence end and pre-FINALIZE call order are not well defined
**Where:** §1.7.3 "Repeated calls"; §11.89 table; PV-30 (R18Δ clause).

**Evidence:**
- §1.7.3 says that on an early exit "(K01–K08, K10–K14, K25, K27), the last call issued by the check that decided".
- §11.89 lists "K02–K07: the call that decided (the commit parse …)" and "K10–K14: the last call issued while evaluating the no-covering rows … (for K12–K14, the last call that computed cand)".
- PV-30 says: "every git call and read is assigned to one computation and position".

**Counterexamples:**
1. **K13/K14.** The deciding check is `FR.fresh`, and freshness() issues no git call. The §1.7.3 text names no call; §11.89 instead names cand's last call. The two are inconsistent.
2. **K11, and K25 at IA7 step 2.** The deciding checks (`refs = ∅`, distinct X) issue no call.
3. **K03.** np(C) is cached from the K02 parse. The last call actually issued is `merge-base --is-ancestor C T`, not "the commit parse".
4. **C12 and non-blob C08** (FP > 20,000, RANGE, E or pid limits, 300 s total) have no failing call. The table covers only "C08–C11" and the blob `cat-file -s` case.
5. **Unassigned order.** The canonical order covers only IA7 step 3 and FINALIZE. Not assigned:
   - IA3–IA6 iteration and their `--is-ancestor` calls;
   - the `covers(h, C)` checks for K10 hits (whether `∃` short-circuits);
   - cand's `rev-list` plus the `diff-tree --cc` loop over G ∈ RANGE (order and short-circuit).

   So "the last call that computed cand", and the first occurrence of an argv-keyed injection inside these computations, are not determinate. FX-C09c's statement "IA2–IA5 issue rev-list, diff and patch-id" also omits their `--is-ancestor` calls; this is harmless to its argument.

**Impact:** R21-05 and PV-30 claim more than the text defines. No fixture outcome moves, but TF determinacy for double failures before FINALIZE is unstated.

**Smallest correction:**
- Replace the §1.7.3 per-exit gloss with "the last git call issued, in issue order, before the decision or failure".
- Fix the §11.89 rows for K03, K10/K11, K13/K14 and K25 step 2, and add C12 and non-blob C08.
- Either define an order and no-short-circuit rule for IA3–IA6, the K10 hits and cand, or narrow PV-30 and residual (q) to FINALIZE and IA7 step 3.
