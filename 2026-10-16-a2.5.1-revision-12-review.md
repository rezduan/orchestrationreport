## 2. Findings

### R12-01 (HIGH): the seven-state opaque classification removes a surviving counted change from relevance, so MERGED is returned without it

**Section:** §1.7.3 Classification and Relevant paths (ii); §11.13; §1.7.4 superseded.

**Evidence.**
- Classification: "A path p is opaque iff, in **any** of Pre, Post, Bu, End, Tb, Tip or Tn, p is … a blob with a NUL…"
- Rule (ii): "p is opaque with entry(End,p) = entry(Post,p) ≠ entry(Pre,p)".
- §11.13: "A path that is text in Pre and Post but binary in Bu, End, Tb, Tip or Tn is now opaque. Relevance is then by (ii) or (iii)."

**Counterexample (ancestry-merge, interim rules).**
1. F0 holds text files f and p.
2. On the branch, C adds L to f and adds L′ to p. A later branch commit C1 adds L2 to p. So End(p) ≠ Post(p), but L′ survives: S_A(L′) = 1.
3. Target Hr edits p (t ≠ b). P = `merge --no-ff (Hr, X)`. The merge conflicts at p and the resolver takes Hr's p, so L′ is absent from Tip. f merges cleanly, so r = e at f.
4. Later, a target commit makes p binary (a NUL byte) in Tn. Alternatively, Hr itself made p binary, so Tb and Tip are binary.
5. p is now opaque. Rule (ii) fails because End(p) ≠ Post(p). Rules (iii) and (iv) do not apply. So p is **not relevant**.
6. Anchoring is trivial: Bu = F0 ⊑ Pre. f is landed. PR = 0, because entry(I.base,p) = entry(I.tip,p). Content: K > 0 from f, k = K, and B excludes p.
7. Result: **MERGED K23**, with CV3 ("replaced on its own branch"), which is also false: L′ survived to End.

The squash form (Option B) behaves the same way. This breaks §1.9 MERGED clause (3) on its own terms: p is "a path where C's counted line change … survives to the branch end", and it is never compared. Without the target-side binary state, p is text, rule (i) fires, and the result is K31 or K30. So this is a regression introduced by the R11-13 fix.

**Impact.** A false MERGED under the rule in force (§13 test 2 stop condition). The trigger needs a text→binary, symlink or gitlink transition at p in some state, plus a later branch edit at p. Rare, but not excluded.

**Smallest correction.** Decide relevance from the branch-side states only. If p is text in Pre, Post and End, apply rules (i), (iii) and (iv) using text counts, even when p is opaque in Bu, Tb, Tip or Tn. Use the seven-state opaque classification only for landing and content. Such a path is landed only if r = e (unverifiable otherwise, in both UR-21 options), and its content is compared by entry. Add a fixture: the counterexample above, expected K30 or K31 in every option.

### R12-02 (MEDIUM): the effect of UR-19 option (b) on FX-K32b and FX-K32d is misstated when UR-21 Option A is adopted

### R12-03 (MEDIUM): the costs listed for UR-21 Option A omit the guard's false blocks, which may be its dominant cost

**Section:** §2.3 UR-21 Option A "Cost"; §11.4; L-21; §9.1 R11-02.

**Evidence.**
- §2.3: "*Cost:* K33 when the guard holds but the unit's diff does not carry C's change".
- §11.4: "Correct squash with the target editing the same file — MERGED (K23aj, K23am), except K33 cases".
- §9.1 says the guard's over-blocking is "Disclosed under L-21", but L-21 does not mention the guard.

**Counterexample.**
1. C adds `</div>` and `<p>x</p>` to a Blade file.
2. Before the squash, the target edits another block of the same file and adds or removes a `</div>`.
3. Tb(`</div>`) ≠ Bu(`</div>`), so the guard fails → unverifiable → K31 under Option A, although C's lines are present.

Any touched line that is common in the file (`}`, `});`, `@endif`, `</div>`, `return;`) fails the guard whenever the target changes that line's count anywhere in the file.

**Impact.** The owner's UR-21 table overstates what Option A rescues. The disclosure exists only in §11.15(d), outside the decision text.

**Smallest correction.** Add the guard false-block class to the Option A cost in §2.3, to §11.4 ("except K33 cases and guard failures on touched lines whose count the target changed, including common lines"), and to L-21. Ideally give the common-line example, and note that the frequency is unmeasured (RT-10).
