### R26-01 — MEDIUM — residual (bb) still states the relevance argument in presence terms; R25-01 not fully applied; PV-33 (4) false again

**Where:** §11.116 residual (bb). This is current text under §0, and PV-33 (4) explicitly includes §11.110–§11.116. The R25 review listed "residuals (bb) and (z)" in R25-01's "Where".

**Evidence:** "(bb) (R20Δ) The relevance argument (§1.7.3) is one line and kind-independent; it assumes only that **'part of C's change is present at the branch end' implies a difference of entry from C's parent**. The next reviewer should attack that implication first."

**Counterexample:** FX-K23be, the packet's own fixture. C's appended copy of L may be the one still present at the branch end, yet entry(End,f) = entry(Pre,f). So the implication that (bb) says the argument "assumes" is false under copy identity.
- The restated §1.7.3 no longer assumes it. Instead it reasons that every survival class implies a state difference, and it says outright that "End can equal Pre while C's own added copy of an identical line is still present".
- (bb) therefore contradicts §1.7.3 and makes the presence claim that PV-33 (4) forbids.

**Impact:**
- There is no outcome effect.
- A binding criterion (PV-33 (4), status B) is again false of the current text, which is the R25-01 defect class in a location R25-01 named.
- The residual also points the next reviewer at a premise the current argument no longer uses. §9 records R25-01 as "Resolved in draft"; that disposition is overstated.

**Smallest correction:**
- Rewrite (bb): "The relevance argument (§1.7.3) uses only that every survival class — by net count, content, kind or mode — implies entry(End,p) ≠ entry(Pre,p). It makes no claim about which copy of an identical line is C's (FX-K23be, L-4)."
- Optionally, reword FX-K23av's "nothing of C's change exists at the branch end" to "by content, none of C's change appears at the branch end", to match the restated argument.

### R26-02 — LOW — the "Revision 20 MERGED, interim not" predicate omits its precondition, and the `binary_present` disclosure misses Kc paths that fail the Tn test

**Where:** header, "Toward AMBIGUOUS" bullet (R26Δ) and the "Field movement" sub-bullets; §11.112; residual (dd).

**Evidence (a):** "exact predicate for 'Revision 20 MERGED, interim not' (every UR-22-independent check passing): **either** K + J = 0, CS = ∅ and some class-5 Kk path (→ K21 …); **or**, otherwise, some class-5 Kc path whose content(Tn) ≠ content(End) (→ K22)". §11.112's own converse adds "**given Revision 20 sufficient**".

**Counterexample (a):** FX-K21l and FX-K21m. Both satisfy branch 1 (K + J = 0, CS = ∅, class-5 Kk), and every UR-22-independent check passes in both. Yet Revision 20 gave **K22** for each: FX-K21l through the Tn rule on f, FX-K21m through b < B. The packet lists both as K22 → K21 movements, not MERGED → K21. So as stated, the predicate is not a characterisation of "Revision 20 MERGED, interim not". It is exact only conditionally. I proved the conditional form: given Revision 20 MERGED, the interim is non-MERGED iff branch 1 or branch 2 holds.

**Evidence (b):** "`binary_present` moves … on **every** such line with a class-5 **Kc** path **whose Tn test passes**" (also §11.112).

**Counterexample (b):** take FX-K21c with a later target change of p, so Tn(p) ≠ End(p).
- Revision 20 (Option B): p ∉ B_B and K + J + B\* = 0, so K21 with `binary_present=0/0`.
- Interim: p ∈ B_int (kind survives) but p ∉ B\*, so K21 with `binary_present=0/1`.
- The outcome does not move but the field does, and the path fails the Tn test, so the disclosure does not cover it.
- The same 0/0 → 0/1 (or b/B → b/(B+1)) movement occurs on K15–K19, K22 and K26 lines. Example: FX-K23bd with Tn(p) ≠ End(p) and a later exact revert gives K18 under both rules.

**Impact:** the disclosure requested by R23-07, R24-02 and R25-03 is still not exact. No MERGED is affected.

**Smallest correction:**
- (a) Prefix the predicate with "Given that Revision 20 is MERGED (every UR-22-independent check passing), the interim is non-MERGED iff …", and use the same wording in §11.112.
- (b) Replace "whose Tn test passes" with: "`binary_present`'s denominator grows by one for each class-5 Kc path, and its numerator by one when that path passes the Tn test."
