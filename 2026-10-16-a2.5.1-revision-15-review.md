## 2. Findings

### R15-01 — MEDIUM — CV1 clause A under UR-19 (a) is false or unchecked under the interim compilation (also breaks PV-28)

**Section:** §1.10 CV1; §11.35; PV-28.

**Evidence:**
- §1.10, clause A under (a): "the unit's base agrees with the fork point on this commit's files (true: AS = every relevant path, and MERGED requires anchoring over AS …)".
- §1.7.3: anchoring compares **Ht**, not Bu: "for a **chained** squash (Bu = X_v …), Ht is the single member of `merge-base --all X_v T`".
- §1.9 (2) correctly says "the unit's **absorbed-target base** agrees with the fork point" and limits it to AS.

**Counterexample 1 (binding-shaped fixture, interim branch): FX-K23al.**
- Bu = X1 = A1, which holds C's sibling edit "f line 10".
- Ht = F0 and Fk = F0, so the result is anchored. Expected: "MERGED K23, segment_base=X1, CV1, CV6".
- entry(Bu, f) = A1(f) ≠ entry(F0, f) = entry(Fk, f).
- So the printed sentence "the unit's base agrees with the fork point on this commit's files" is **false** for the file f.
- The packet itself makes this point in §11.5 (7): Bu = X1 versus Fk "differ at f" was the R11-04 false block that Ht removed.

**Counterexample 2: "this commit's files" ⊋ AS.**
- C edits f (adds L) and g (adds L2). Branch commit C1 later removes L2, so g has no touched line, g is not relevant, and superseded = 1.
- The branch back-merges target commit Hb, which edits another line of g after C. Squash; the target does not touch f.
- Under (a), AS = {f}, so the result is anchored at f, landed (r = e at f), MERGED with CV1 and CV3.
- At g, Ht(g) = Hb(g) ≠ F0(g) = Fk(g). Yet CV1 asserts agreement "on this commit's files". That is an anchoring claim outside AS, which PV-28 forbids, and here it is false.

**Impact:**
- The in-force compiled caveat (P-21 PDB, interim (a) × B) states a fact that is false on a fixture the packet expects to be MERGED.
- §11.35's first row ("true: AS = every relevant path") and §11.36's "misleading text: none found" are wrong.
- R14-02 is therefore only partially resolved.

**Smallest correction:**
- Reword clause A (a) to match §1.9 (2), for example: "the target state the branch had absorbed before integration agrees with this commit's fork point on each file whose change by this commit survives". Avoid "unit's base" and "this commit's files".
- Add FX-K23al's caveat text to PV-28 or §11.35 as a check case.

### R15-02 — MEDIUM — A Step 0 failure (K28/K29) does not short-circuit AS, AN and landing in §1.7.3 / §1.8.3; only §4 does

**Section:** §1.7.3 Step 0, "Anchoring scope AS", Step 2; §1.8.3 "Compute first"; §4 `anchoring()` and `finalize()`.

**Evidence:**
- §1.8.3: "Compute first … (1) Bu (structural, ancestry-merge only); (2) AS, then AN …; (3) LD — only if AN = ANCHORED". Nothing says (2) and (3) are skipped when (1) yields 0 or more than 1 bases.
- §1.7.3 (b): "For ancestry-merge … AS = ∅"; "If AS = ∅, AN = ANCHORED"; Step 2: "executes only when AN = ANCHORED (including AN = ANCHORED because AS = ∅)".
- §4, by contrast, returns BU_NONE or BU_MULTI from `anchoring()` before AS, so landing is skipped.

**Counterexample:**
- Take the FX-K28 history (P merges an unrelated-history branch containing C), with C changing f. The target has its own f, and the merge is resolved to the target's f, so r ≠ e. Run it under UR-19 (b), or add FX-C13b's landing-phase hook.
- **Reading of §1.7.3/§1.8.3:** AS = ∅, so AN = ANCHORED and landing runs.
  - With the hook, the result is C13.
  - Without the hook, the merge table must evaluate "t = ub" with ub = entry(Bu, f) and no Bu. That is undefined; C14 is a plausible outcome.
- **Reading of §4:** K28.
- Under (a), §1.7.3 anchoring step 2 ("Ht: Bu for ancestry-merge") is evaluated with Bu undefined, and the text does not say what happens.
- The two conforming readings give different outputs. This is the R14-01 defect class: Step 0's own failure has no stated continuation.

**Impact:** The R14-01 and PV-27 claim that the three sections "agree" is false on K28/K29 histories, and the outcome becomes implementation-dependent.

**Smallest correction:**
- In §1.7.3 Step 0 and §1.8.3, add: "If the Bu count gives K28/K29, AS, AN and LD are not computed (AN := that row); EV, PR and CK still run."
- Add a fixture: FX-K28 plus the landing-phase hook → K28 in every option.

### R15-03 — LOW (uncertain) — Determinacy under injected read failures depends on per-computation read sets that are not specified

**Section:** §11.32 (2); residual (q); §1.7.4; FX-C13.

**Evidence:** "a failure on a state that content (or events, or PR) also reads gives C13 whatever AN is." But no text says which blobs content reads. For example, j_inc's formula Σ min(S_R, max(0, Tn − Tip)) can be computed lazily, so blob(Tip, p) is read only where S_R > 0.

**Counterexample:**
- Take a FX-K32d variant: C adds L and L2 to f; Hf adds L only; the back-merge G(f) = Hf + L2; S adds L2, so Tip(f) ≠ Tb(f); a later target commit Z edits f, so Tn(f) ≠ Tip(f). J = 0.
- Under (a), the result is K32 and landing is skipped. Under (a) × B, landing would compare entries only anyway.
- Inject a failure on `cat-file blob <oid of Tip(f)>`:
  - an implementation that eagerly counts every state gives TF;
  - a lazy implementation never reads that blob and gives K32.
- FX-C13 ("blob read failure → C13", status B) has the same problem: it does not say which blob.

**Also:**
- §11.32 calls a failed blob read "C13 (TF io)", but §1.3 maps any non-zero git exit to C10.
- §1.4 is written as if every C row is decided by the computations alone; it is not clear which applies to a harness substitution.

**Smallest correction:** Pin a read set per computation, or restrict TF-injection fixtures to phase hooks. Name the injected blob in FX-C13, and state whether the injected failure maps to C10 or C13.
