## 2. Findings

### R17-01 — HIGH — An opaque change drops out of relevance after a mode-only branch edit, giving MERGED with C's binary content absent from Tip

**Sections:** §1.7.3 rule (ii) and "Why a surviving change can no longer drop out [R]"; §1.7.4 (B, b, superseded); §1.9 MERGED (3); §11.30 / §11.36 ("A surviving change dropping out of relevance: impossible").

**Evidence**
- Rule (ii): "p is C-opaque and entry(End,p) = entry(Post,p) ≠ entry(Pre,p)". `entry` compares (mode, type, oid).
- Rule (iii) applies only when *C* changed the mode.
- §1.7.3 states: "A change that survives to End (counted, uncounted, opaque or mode) satisfies one of them".

**Counterexample** (ancestry-merge, interim (a) × B)
- F0 holds binary file `bin` = v1 (100644) and text file f.
- Branch: C changes `bin` from v1 to v2 (content only) and adds line L to f. A later branch commit D runs `chmod +x bin`, so End(bin) = (100755, v2).
- Target: Hr changes `bin` from v1 to v3.
- P = `merge --no-ff` (Hr, X). `bin` conflicts and the resolver takes Hr's content, so Tip(bin) = v3. f merges cleanly.
- A conflict-free variant also exists: the target makes the same v1 → v2 change first, the branch back-merges it after C, then D runs chmod, then the target changes `bin` to v3. The 3-way merge then cleanly yields v3/100755, and anchoring on f passes.

**Derivation**
- `bin` is C-opaque. (ii) fails: entry(End) = (755, v2) ≠ entry(Post) = (644, v2). (iii) fails: C made no mode change. So `bin` is **not relevant**.
- AS = {f}. Ht = Bu = F0 = Pre, so anchoring passes trivially.
- f: r = e, so it is landed.
- `bin` is in neither B nor b, so b = B = 0. superseded = 1.
- Content state 3 (k = K = 1) → **MERGED K23**, caveats CV1, CV3, CV6.

**Why the output is false**
- C's binary content change (v2) is present at the branch end but absent from Tip (v3).
- CV3 says the change was "replaced on its own branch before integration". The branch only changed its mode.
- CV1 clause L ("each such file's surviving change is reflected … by file equality") is false in the natural reading for `bin`.
- The text analogue gives K31: a C-text path with a later chmod stays relevant by (i), and r ≠ e then blocks it. The asymmetry exists only for opaque paths.

**Impact:** a state-level false MERGED under the packet's own definition in §11.36 / §1.9 (3), plus a false CV3. It is reachable under every UR-19 × UR-21 cell, including the interim cell.

**Smallest correction**
- In rule (ii), and in B, b and superseded, compare (type, oid) for C-opaque survival and leave mode to rule (iii).
- Landing keeps full-entry equality (r = e), so the example becomes K31 or K30.
- Add a fixture: binary change plus later branch chmod plus target-side content change, expected K31.

### R17-02 — MEDIUM — CV1 clause A (option (a)) is still false on R16-01's own counterexample, and broader than rules (ii) and (iv)

**Sections:** §1.10 CV1; §11.45; §9.00000 R16-01; PV-28.

**Evidence**
- Clause A covers "every file whose reordering or whitespace-only change by this commit is still unaltered at the branch end; a reordering … that was later edited on the branch … is not covered".
- Rule (iv) instead requires **entry(End,p) = entry(Post,p)**: the whole file, not the reorder.
- §11.45 row 1 describes the reviewer's case as "C swaps two lines of g; a back-merged target edit Hb changes **another line** of g". It then says the reorder "was 'later edited on the branch'".

**Counterexample 1: the reviewer's case**
- The swapped lines are untouched at End, because Hb edited another line. The reorder is "still unaltered at the branch end", so the clause claims g is covered.
- g is not relevant and not in AS. Hb is a back-merged target change on g, so entry(Ht, g) ≠ entry(Fk, g). The clause's claim "agrees with this commit's fork point" is concretely false.

**Counterexample 2: mixed file**
- C adds L to f and swaps lines M and N. A later branch commit deletes L.
- (i) fails (no touched line). (iv) fails (A(L) > 0). The swap is still unaltered, so the clause claims coverage.

**Counterexample 3: rule (ii) wording**
- The clause covers files "where some … binary … or file-to-directory change … survives". Rule (ii) needs exact entry equality.
- The `bin` + chmod case of R17-01 shows this: the binary change survives but `bin` is not covered.
- File-to-directory variant (uncertain on git's merge details): C replaces file d by directory d/{x}. The target independently replaces d by d/{z} and is back-merged after C. Then End(d) = tree{x, z} ≠ Post(d), so d is not relevant, but the clause claims it.

**Impact:** CV1 (a), the interim compiled text, asserts an anchoring comparison that was not made. That violates PV-28. R16-01 and R15-01 are not resolved.

**Smallest correction:** reword clause A to the rule text. Suggested wording:

> "on every file where a line this commit added or removed is still counted at the branch end; on every non-text file whose entry at the branch end is exactly this commit's; on every file whose mode change by this commit is unchanged; and on every file this commit changed only without counted lines (reorder, whitespace, empty file) that is byte-identical at the branch end; no other file is covered, even if part of this commit's change remains in it".

Correct §11.45 row 1.

### R17-03 — MEDIUM — The binding fixture FX-C10d contradicts the canonical order

**Section:** §7.1 FX-C10d (status B); §1.7.3 canonical order; §11.47.

**Evidence:** the setup is a "Default MERGED setup … (2) the Tn blob at g is 9 MiB". The expected result is C10, with "Failure (2) (CK, path g, Tn) is never reached".

**Counterexample**
- The default setup says "the target did not touch C's paths". With X = C, that gives Tn(g) = Tip(g) = End(g) = Post(g): one blob oid.
- The canonical order runs **relevance first**. Relevance reads "entries and blobs of Pre, Post, End" for f, then for g.
- So `cat-file blob <g-oid>` (9 MiB) is read during relevance at g. That is before LD reads `ls-tree <Tip> -- f`.
- Result: **C08**, not C10.
- If the failure is injected by argv (the only kind of naming §1.7.3 allows), the identical call fails at its first occurrence. "Read in its own position" cannot single out the Tn position.

**Impact:** a binding RT-01 fixture would fail on a conforming implementation, or would reward a non-conforming read order.

**Smallest correction:** state a later target commit Z that replaces g with a distinct 9 MiB text blob, so that Tn(g) ≠ End(g). Alternatively, inject failure (2) on a call that occurs only in CK. Also state that an argv-keyed injection fails at the first occurrence of that argv.

### R17-04 — LOW — The read discipline is still not fully determinate; the three sections disagree on order

**Sections:** §1.7.3 read discipline and canonical order; §1.8.3; §4 `anchoring()` and `finalize()`; §6.1; §1.8.3 diagnostics; PV-27, PV-30.

**(a) Relevance vs Bu**
- §1.7.3 orders "relevance → Bu (Step 0) → AS …".
- §1.8.3 ("(1) Bu … (2) AS") and §4 (`anchoring()` computes Bu, then `in_scope_paths`) compute Bu first.
- Injection on an ancestry merge: `merge-base --all P^1 P^2` exceeds 60 s, and `ls-tree <P^2> -- f` exits 128.
  - §1.7.3 order gives **C10**.
  - §4 order gives **C09**.

**(b) Candidate anchoring is unordered across candidates**
- IA7 step 3 / §4 compute AN "for each candidate" with no stated candidate order.
- Example on FX-K25c: V2's `merge-base --all M1 A0` times out, and V3's `merge-base --all A1 T` exits 128. The result is C09 or C10 depending on which candidate is processed first.

**(c) Calls outside every read set**
- These calls appear in no computation's read set or position:
  - §6.1 u_I, u_C, r_I, r_C (diff and patch-id);
  - `later_commits` (`rev-list --count T --not I.tip -- paths(C)`);
  - `c_paths_in_unit` (`diff-tree` on IU).
- It is undefined whether the diagnostics run on lines that print `-` (K28–K34).
- Example: FX-K32a under (a) with a failing `rev-list --count` gives K32 under one conforming reading and C10 under the other.

**Impact:** only the TF/K code under failures differs; no MERGED is affected. PV-30's claim that "every computation's read set is defined" and PV-27's claim that the sections agree are not yet true.

**Smallest correction**
- Put relevance first in §1.8.3 and §4, or move it after Bu in §1.7.3.
- Order candidates by (OID(seg_base), OID(S)).
- Assign §6.1 and the diagnostics to EV and CK, with a fixed position and an "always computed" rule.
