## 2. Findings

### R25-01 — MEDIUM — the current §1.7.3 still makes a copy-absence claim; the universal relevance argument is worded in provenance terms; PV-33 (4) is violated

**Where:** §1.7.3, "Why no surviving change can drop out of relevance (R20Δ)" (line 714). This is current text under §0. PV-33 (4); residuals (bb) and (z).

**Evidence:** "If any part of C's change at p — **a line**, an object, a kind or a mode **that C put there** — is still present at the branch end, then the branch end differs from C's parent at p … Contrapositive: a path that is not relevant has entry(End,p) = entry(Pre,p); … **no** part of C's change exists at the branch end. … its counted and opaque changes are superseded (CV3), truthfully, **because nothing of them is at the branch end**."

This contradicts two other parts of the current text:
- §1.7.3 "Survives": "'does not survive' (S_A = S_R = 0) **does not establish that C's copy is absent** (L-4)".
- FX-K23bb: "C's own L is still present; only a pre-existing copy was removed."

**Counterexample (copy-level analogue of FX-K23bb):**
- Pre f = "L\nL\n". C appends L, so Post = "L\nL\nL\n" and A(L) = 1. A later branch commit deletes the **first** line, so End = "L\nL\n", which is byte-identical to Pre.
- entry(End,f) = entry(Pre,f), so f is not relevant. S_A = 0 and superseded = 1.
- By the packet's own FX-K23bb reasoning, C's appended L is still present and only a pre-existing copy was removed. Yet §1.7.3 asserts that "no part of C's change exists" and "nothing of them is at the branch end".
- So the stated implication ("a line that C put there is still present ⇒ End ≠ Pre") is false under copy identity. It holds only when "present" is read as net state.

**Impact:**
- No state-level false MERGED: CV3's own text stays true.
- A binding criterion (PV-33 (4), B) is violated in the normative section.
- The argument that residual (bb) asks reviewers to attack first is stated in the provenance terms the series has banned since R22-01.
- This is the R24-01 defect class, now in §1, where the §0 precedence rule cannot help.

**Smallest correction:** restate the argument in state or net terms. For example: "If the branch-end entry at p differs from Pre's in any respect that C's change produced (content, kind or mode), p is relevant. Contrapositive: a non-relevant path has End = Pre at p, so by net count and by content none of C's changes appears there (S_A = S_R = 0; content(End) = content(Pre)). Which identical copy remains is not established (L-4)." Replace "truthfully, because nothing of them is at the branch end" with "and CV3's text is true for them (§11.85)". Add the example as a fixture or as a note next to FX-K23bb.

### R25-02 — MEDIUM — FINALIZE's EV leaves calls in §6.2, §6.3 and §6.5 without a position; one genuine fault in FINALIZE can change the outcome

**Where:**

- PV-30 R18Δ ("every git call and read is assigned to one computation and position (§11.56)"); §11.56's table.
- §6.2 (np(Q)), §6.3 (lineage), §6.4 CR2 under P-14, and §6.5 (ordering).

**Evidence:** EV also issues the following git calls, and none of them is in EV's read set, the canonical order or §11.56:
- `cat-file commit <Q>`, to decide np(Q) ≤ 1 versus Q^1 (§6.2);
- `merge-base --is-ancestor <I.lineage_root> <Q>`, the qualification check (§6.3);
- `merge-base --is-ancestor <rep(e₁)> <rep(e₂)>`, for the total-order test (§6.5);
- under P-14, CR2's `Q_X ⊑ Q_M^2` and `Q_X ⋢ Q_M^1`.

How many of these calls are issued, which pairs, in what order, and whether they short-circuit are all unspecified. The whole-read-set rule cannot constrain calls that are not in a read set.

**Counterexample (one genuine fault, FINALIZE only):**
- Take FX-K18f's shape with three exact reverts R1 ⊑ R2 ⊑ R3 on FP after the integration. A natural timeout hits `merge-base --is-ancestor <R1> <R3>`.
- An implementation that compares every pair issues that call and returns **C09**.
- An implementation that sorts by comparisons infers R1 ⊑ R3 from R1 ⊑ R2 and R2 ⊑ R3, never issues the call, and returns **K18**.
- Both conform.
- Likewise, §6.3 does not say whether qualification is computed for every record or only for reverts, so a fault in the lineage check of a reapply record gives C09 under one implementation and the ordinary row under another.

**Related duplicate argvs (present C):** for ancestry-direct and ancestry-merge, lineage_root = C. The records `rev-list T --not I.tip` include the FP commits newer than P, and `oldest_fp_container` (linear from the newest end, or by bisection) may already have issued `merge-base --is-ancestor C <X>` for exactly those X. That is a pre-issue route in **present-C** histories. It contradicts §11.106's statement that present-C histories avoid this, and it is missing from R24-04's examples (see R25-04).

**Impact:**
- FINALIZE's "determinate first failure" and PV-30's "every call assigned" are false for EV.
- Unlike R24-04, a single fault is enough.
- RT-02's cross-implementation reproducibility is not guaranteed.
- No false MERGED results: a skipped comparison is implied by transitivity.

**Smallest correction:** add to EV's read set and canonical order, per record in `rev-list` output order: parse Q → its pid → (if e is non-NULL) its lineage check. Then add §6.5's comparisons as all ordered pairs of distinct representatives in (rank, rank) order, with no transitivity short cut, followed by CR2's calls when P-14 is adopted. Alternatively, add EV's §6.3–§6.5 calls to the "Not determined" list, L-30 and UR-23, and narrow PV-30 accordingly.
