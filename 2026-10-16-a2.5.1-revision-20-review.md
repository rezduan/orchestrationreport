### Evidence per area

**Area 1: universal relevance/survival claim (attacked first).**

R(p) := entry(End,p) ≠ entry(Pre,p) over p ∈ paths(C). entry is the full (mode, type, oid) triple, with ⊥ equal only to ⊥. I tried to build a history in every mode where some part of C's change at p is present at End while entry(End,p) = entry(Pre,p). None exists. At a single path, equal entries mean identical bytes, mode and type, so End *is* Pre there. This is true of a state, not a reasoning step, and it holds the same way in direct, merge, first-integration squash and chained squash, because End is just I.end in each mode.

Specific attempts, none of which broke it:
- **Duplicate-line count tricks** (C adds L; a later commit removes a pre-existing copy of L): End(L) = Pre(L) but the blob differs, so the path is relevant. The counts make it superseded, which is the known L-4 limit.
- **Mode-only round trips:** a later chmod back gives End ≠ Pre unless the bytes are also restored.
- **File ↔ directory:** `ls-tree --full-tree X -- d` returns the 040000 entry, so the kind change is visible.
- **gitlinks, symlinks, root C** (Pre = empty tree).
- **Merge-commit C in direct mode** (Pre = C^1).
- **Chained segments:** End = X2, not the branch tip.

I also re-checked "every survival class implies relevant" (S(i)–S(iv)) for each sk branch, including Post = ⊥ and Post = tree. It holds.

The one scope boundary, which is legitimate but worth stating: the argument is per path in paths(C). A later branch rename moves C's content to a path outside paths(C) (`--no-renames`). Then f is relevant with End(f) = ⊥, it lands vacuously when Tip(f) = ⊥, and C's content at the new path is never examined. The result is K21 or MERGED+CV3, never a state-level false MERGED, but CV3's "replaced" is really "moved". This is consistent with L-4 and the non-goals, so it is not filed.

### R20-01 — MEDIUM — K22's non-textual-Tn rule now fires on paths where nothing of C survives

**Sections:** §1.7.4; L-25; §1.7.3 "Relevant (subject to landing)"; §11.75; L-29.

**Quoted evidence.**
- §1.7.4: "**Relevant C-text path with a non-textual Tn** (R13Δ, R12-01): C's surviving lines cannot be counted in the current target, so the content state is **insufficient → K22** (applied in states 3–5)."
- §1.7.3: "Selecting too much can only add K30/K31/K32/K34 results (L-29)."
- §11.75: "No binding (Bo/B) fixture moved".

**Counterexample (squash, interim (a) × B).**
1. F0 has text files f and g. C adds L to f and Lg to g.
2. A later branch commit D replaces f with a binary blob, keeping mode 100644. X = D.
3. The target is untouched before and after the squash.
4. Landing: f and g are both relevant (End(f) is binary ≠ Pre(f)) and both have r = e, so both land.
5. Content: f is C-text with a non-textual End, so S_A = S_R = 0 by definition and superseded = 1. g gives K = k = 1, so this is state 3.
6. f is a *relevant* C-text path and Tn(f) is binary, so the rule above fires: **K22 `content-missing`**.

In Revision 19, f was not relevant (S(i) fails and it is not C-opaque), so the result was MERGED with CV1, CV3, CV6. That earlier result is not false: f landed and CV3 is true.

The same shift happens when End is textual but superseded (the FX-K31ab shape with the target untouched) and a later target commit makes f binary.

**Impact.**
- Fail-closed, so no false MERGED.
- The reason text and L-25's rationale ("C's surviving lines cannot be counted") are false here, because no C line survives at f.
- The packet's normative claim about which results over-selection can add is wrong. It also omits K25: under (a), larger per-candidate AS sets in IA7 step 3 can create or resolve anchoring disagreements, which still never yields MERGED.
- The regression sweep and L-29 do not disclose any of this.
- This is the reverse of the separation R20 promises: a relevance-keyed rule deciding something that is about survival.

**Smallest correction.**
- Restrict the rule to "a C-text path with a touched line (survival class S(i)) whose Tn is non-textual", in §1.7.4, the state-3–5 note, L-25 and PV-23.
- Alternatively, keep the rule as written and disclose it in L-29 and §11.75.
- Either way, correct the §1.7.3 sentence to "can only add AMBIGUOUS results (K22, K25, K30–K32, K34); it can never add a MERGED".

### R20-02 — LOW — the repeated-calls sequence literally includes snap1

**Section:** §1.7.3 "Repeated calls" (R20Δ, R19-05).

**Quoted evidence:** "the sequence is every git call the helper issues after snap0a, in issue order — preflight, resolve_target, snap_refs, decide() …, IA1–IA7, FINALIZE … a call whose argv was already issued earlier in the sequence is answered from that earlier result and not issued again".

**Counterexample.** snap1's `snap_refs()` issues the same `for-each-ref --format='%(objectname) %(refname)' refs/heads/ refs/remotes/origin/` argv as snap0b (and the same T-resolution argv, if snap_refs re-resolves T). Read literally, it is answered from cache, so S1r = S0r always and the (T, RH) comparison is vacuous. D02 is still caught by the file records, which cover `refs/heads/`, `refs/remotes/origin/` and `packed-refs`, so the practical loss is small. The listed range stops at FINALIZE, but "every git call … after snap0a" includes snap1, so the text is ambiguous.

**Impact.** A determinism/semantics ambiguity; the ref-record check could be implemented as a no-op.

**Correction.** Add "The sequence ends with FINALIZE's last call; snap1's calls are always issued afresh and never answered from it."

### R20-04 — LOW — survival-key asymmetry persists in content and CV3

**Sections:** §1.7.3 survival key; §1.7.4 B, b, superseded, state 2.

**Quoted evidence:** sk is "kind(X,p) … when kind(Post,p) = text and kind(Pre,p) is non-textual"; "content(X,p) otherwise (C's post-state is a binary …)".

**Counterexample (two mirror histories, target untouched so both land).**
- *History 1:* C turns text p into binary v0 and adds Lg to g; a later branch edit makes p v1. Then sk(End) ≠ sk(Post), so p is superseded and excluded from B. After a later target commit changes p to an unrelated text t8 (PR = 0), the result is **MERGED with CV3**, and Tn(p) is never checked.
- *History 2 (mirror):* C turns binary p into text t1; a later edit makes it t2; Z makes it binary v8. Here p is in B, and b fails, giving **K22**.
- When p is C's only path, history 1 gives K21 `superseded-in-branch` although C's kind change (text → binary) is still there.

**Impact.** No false MERGED under B-08, which does not claim current presence. But the content check and CV3/K21 wording treat symmetric kind transitions inconsistently, which is the content-side remainder of R19-01. Fail-closed or neutral.

**Correction.** Either key sk by kind for every kind-changing C (Pre kind ≠ Post kind), or disclose the asymmetry in L-27 and residual (j).
