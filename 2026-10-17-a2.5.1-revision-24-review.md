### R24-02 — LOW — the reason- and field-movement disclosures are imprecise and incomplete
**Where:** header bullets "Reason movement K22 → K21" and "Field movement"; §11.87 (the R24Δ sentence); residual (dd).

**Evidence:**
- The header: "a commit with a path p of case (a) above (C-text, End non-textual, Tn non-textual, **A > 0**) and a class-5 Kk path q …, and no counted surviving line, was K22 … It is K21 under the interim (CS = ∅ and K + J = 0 → state 2) … Neither old nor new result under the interim is MERGED."
- §11.87: "a commit that also has a class-5 Kk path and no counted surviving line goes to K21, not MERGED."

**Counterexamples:**
1. **CS = ∅ is not implied by the stated conditions.** Take FX-K21l plus a binary r that C changes v0 → v1, with End = Tn = v1. Then CS = {r}, the interim reaches state 5 with b = B, and the Tn rule needs S(i), so the result is MERGED + CV3, not K21. "Goes to K21" and "neither … is MERGED" are therefore false as stated.
2. **"A > 0" is unnecessary.** If C only removes lines at p (R > 0), or makes an uncounted change there, the movement is the same.
3. **Case (b) is omitted.** Take FX-K23bc's f (End textual, no touched line, Tn binary) plus a class-5 Kk q. Revision 20 gives K22 (q ∈ B, state 5, Tn rule on every relevant C-text path); the interim gives K21.
4. **The b < B case is omitted, with no case-(a) or case-(b) path at all.** Take FX-K21d with a later target commit that changes p to unrelated text t8. Revision 20 (Option B): p ∈ B, b < B → K22. Interim: state 2 → K21.
5. **A field movement on MERGED lines is undisclosed.** Take H1 with Tn = End plus g (text → binary v0, branch → v1). Revision 20: p ∉ B, so `binary_present=0/0`. Interim: p ∈ B, so `1/1`. Both are MERGED + CV3.
6. **The header's "Toward AMBIGUOUS" bullet still lists only FX-K21d and K22m.** It omits K21f and K21k, which (dd) lists.

**Impact:** the disclosure that R23-07 asked for is still partial. It claims a predicate that has false positives and misses true cases. No MERGED is affected beyond case (a), which was already disclosed.

**Smallest correction:** state the predicate as: "the interim is in state 2 (K + J = 0, CS = ∅, every C-opaque change outside B\*), while Revision 20 / Option B is in states 3–5 and insufficient (a relevant C-text path with non-textual Tn, or b < B)". Add the `binary_present` movement for class-5 Kc paths, and add K21f and K21k to the header bullet.

### R24-03 — LOW — the unspecified pre-FINALIZE list is still incomplete: FP's call has no position
**Where:** §1.7.3 "Order guarantees" (straight-line list); L-30; UR-23; §11.89's C08 count row and its "Pre-FINALIZE order" paragraph.

**Evidence:**
- The straight-line list is "preflight, resolve_target, snap_refs, then decide()'s checks — K01 …, C15 …, K02 …, `C ⊑ T`, then … IA2". FP (`rev-list --first-parent T`, limit 20,000) appears in no step and in no unspecified item. `oldest_fp_container` is described only as "up to |FP| `merge-base --is-ancestor`" calls.
- §11.89's paragraph says "the internal order and short-circuiting of IA2–IA6, the K10 shape-hit tests and cand are unspecified". It names three computations, not six, while §11.100 says that §11.89 "marks rows … instead of repeating it".

**Counterexample:** a repository whose first-parent history of T has more than 20,000 commits, and C = a valid hex id with no object.
- An implementation that computes FP lazily (inside `oldest_fp_container` or IA2) returns K01 GONE.
- One that computes FP eagerly at decide() entry returns C08.
- Both conform, because §4 never places FP.
- The same happens for K03, K04, K06, K07, K27 and K08 runs.

**Impact:** a further R23-04-type gap. The C08 limit is excluded from the determinacy claim, but the claim that pre-FINALIZE calls follow §4's straight-line steps is incomplete, and FX-C08's FP case has no defined position.

**Smallest correction:** place FP's call (for example, "FP is computed once, on first use, by `oldest_fp_container` (present C) or IA2 (absent C)"), or add "the FP `rev-list`" to the unspecified list in all six places. Repair §11.89's paragraph to the six-name list or to a reference.

### R24-04 — LOW — "determinate first failure in FINALIZE" is overstated, because the argv and pid cache can pre-issue FINALIZE calls in unspecified pre-FINALIZE computations
**Where:** §1.7.3 ("a determinate first failure are specified only for IA7 step 3 and FINALIZE"; "no implementation may reorder reads to reach a different first failure"); the new pid key.

**Evidence:**
- An argv already issued is answered from its first result.
- A §6.2 record pid, pid(parent0(Q), Q), for a non-merge Q ∈ `rev-list T --not I.tip` has the same DIFF argv as PMAP_O's pid for Q ∈ SOTHER, because RANGE contains Q.
- u_C = pid(parent0(C), C) equals IA3's pid(B_C, C) when parent0(C) = B_C.

**Counterexample (absent-C squash, covering V entry, two genuine faults):**
- Q, a target commit after M, has a missing blob, so its DIFF exits 128.
- A relevant file at End is 9 MiB (blob limit).
- An eager PMAP_O fails in IA2 with C10. A lazy PMAP_O reaches FINALIZE, where relevance fails first with C08.
- Q's call is reached under both orders, only at different positions, so neither "one order reaches, another skips" nor the FINALIZE guarantee describes this.

**Impact:** a narrow overclaim: two genuine faults are needed, and every current fixture avoids it (C10f, C11 and S11d use a present C on purpose).

**Smallest correction:** add to "Not determined": "which failure comes first when a FINALIZE call's argv may already have been issued by an unspecified pre-FINALIZE computation (e.g. §6.2 record pids of SOTHER commits; u_C when parent0(C) = B_C)".

### R24-06 — LOW — CV3's line unit reads as one unit per line, but superseded counts one unit per copy
**Where:** §1.10 CV3 ("Each is counted either as **a net difference in the number of copies of a line** …"); §11.85 ("count unit").

**Counterexample:** C adds three `}` (A = 3) and the branch removes all three. Then superseded = 3, and CV3 says "3 of this commit's changes … each counted as a net difference in the number of copies of a line", which suggests three distinct lines. The quantity is Σ(A − S_A), one unit per copy.

**Smallest correction:** "each missing or extra copy of a line (net count) …".

### R24-07 — LOW — two gaps in the pid-pipeline key
**Where:** §1.7.3 "pid pipelines"; §1.12 "pid computations 20,000"; §6.2 ("A pid failure → C11").

**Evidence and counterexamples:**
1. Whether a cache-answered pid counts toward the 20,000 limit is unstated. Even in FINALIZE, ancestry-direct u_C repeats u_I's argv (and r_C repeats r_I's), so a run near the limit is not determined.
2. The key names the stages "the DIFF's exit, or the `patch-id` stage's output or exit". §1.3 maps a non-zero exit to C10, but §6.2 says "A pid failure → C11". A DIFF or patch-id exit failure in §6.2 is therefore C10 by §1.3 and C11 by §6.2 (FX-C10f shows C10 for the §6.1 DIFF).

**Smallest correction:** "a cache-answered pid is not a computation" (or "is"); and in §6.2, "a malformed `patch-id` output → C11; any non-zero exit → C10".
