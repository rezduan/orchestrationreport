## Findings

### R18-01 — HIGH — Rule (ii) still drops a surviving change when C's post-state is textual but its pre-state is not

**Section:** §1.7.3 "C-text and C-opaque paths", rule (ii), "Why a surviving change cannot drop out"; §1.7.4 superseded and B; §11.53.

**Evidence:**
- "A path p ∈ paths(C) is **C-text** iff Pre and Post are both textual at p; otherwise it is **C-opaque**."
- "(ii) p is C-opaque and **content(End,p) = content(Post,p) ≠ content(Pre,p)**", where content = (kind, oid) for text.
- "Survival is judged on **content** … content(X,p) for (ii) … so it cannot make a surviving content change irrelevant."
- §11.53's only rows for these kinds have "—" in the "Later branch-side edit" column ("directory → file | — | (ii) | (ii) by (kind, oid)"). The later-edit case for an opaque→text change was never derived.

**Counterexample (ancestry-merge, interim (a) × B, everything binding):**
1. F0: `bin5` is binary (100644, v0), and g is a text file.
2. Branch br: C replaces `bin5` with text content "L1\nL2\n" (100644, text t1) and adds Lg to g. A later branch commit D appends "L3" to `bin5`, so End(`bin5`) = (text, t2).
3. Target Hr changes `bin5` to binary v3. P = `merge --no-ff` (Hr, X). `bin5` conflicts and the resolver takes Hr's binary v3. g merges cleanly.
4. `bin5`: Pre is binary, so the path is C-opaque. (ii) fails: (text, t2) ≠ (text, t1). (iii) fails: no mode change. (i) and (iv) do not apply to C-opaque paths. So `bin5` is **not relevant**.
5. AS = {g}. Bu = F0 ⊑ Pre, so anchoring is trivial. g: r = e, landed. paths_unlanded = 0/1.
6. PR = 0: entry(Hr, `bin5`) = entry(P, `bin5`). No events.
7. Content: ΣA = 1 and K = k = 1 for g. B = 0, so b = B. superseded = 1 (a C-opaque content change with content(End) ≠ content(Post)). State 3 is sufficient.
8. Result: **MERGED K23, CV1, CV3, CV6**.

Why this is false:
- C's surviving change at `bin5` is absent from Tip. C's lines L1 and L2 are still in End (D only appended), but Tip holds the target's binary.
- CV3 says "1 of this commit's changes were replaced on its own branch before integration", which is false: the change was extended, not replaced.
- If the same edits were made to a text file, rule (i) would make the path relevant, and r ≠ e ∧ t ≠ ub would give K31.

The same construction works for:
- **symlink→text** and **gitlink→text**.
- **directory→file:** C deletes `d/x` and adds file `d`, and the branch later edits `d`. The `d/x` deletions land as ⊥ = ⊥ whenever the merge result has file `d`, so an evil or hand-resolved merge that drops C's lines in `d` gives MERGED.

There is also a variant that needs no conflict. Take a clean squash, then a later target commit Z that overwrites `bin5`. `bin5` is in neither B nor K, so no content check notices the loss: MERGED, where the text analogue gives K22. And if C's only change is `bin5`, the result is K21 "superseded-in-branch" even though the change survives (AMBIGUOUS, so low impact by itself).

**Impact:** a state-level false MERGED in the rule in force, plus a false CV3. The universal claim in §1.7.3 and §11.30 ("none found now") is falsified a second time.

**Smallest correction:** for a C-opaque path whose Post kind is text (Pre non-textual), judge survival by **kind**, as is already done for trees. That is: relevant iff kind(End,p) = kind(Post,p) = text and content(Post) ≠ content(Pre). Exclude such paths from superseded while they are relevant. Landing stays state equality, which gives K30/K31 when r ≠ e. This is fail-closed, and its cost should be added to L-26 (or a new L-27). An alternative is to treat such a path's text lines as C-text counts with Pre(L) := 0, but that is a larger change. Add fixtures for binary→text plus a later branch edit (merge and squash), and for directory→file plus a later edit.

### R18-02 — MEDIUM — CV1's covered-files sentence is still not exactly rules (i)–(iv)

**Section:** §1.10 CV1; §11.54.

**Evidence:** "each file where a line this commit added is still present … by the line counts at the branch end; each non-text file whose kind and object at the branch end are exactly this commit's; … no other file is covered".

**Counterexamples:**
- **Over-claim:** in R18-01's history, a reader of CV1 takes `bin5` as covered, because lines C added (L1, L2) are still present at the branch end. Clause L then asserts "each covered file's state is reflected in the integrated state by file equality". That is false for `bin5`. Rule (i) excludes `bin5` only because "C-text" is a technical precondition that CV1's words do not carry.
- **Under-claim:** a binary→text change unchanged at End is relevant by (ii) and is in AS. But it is not a "non-text file" (it is text at End and Post), and no counted line or "without counted lines" clause applies. CV1 says "no other file is covered", so the covered set in CV1 ≠ AS. That contradicts the claim "under (a) the covered files are exactly AS". It is harmless as an under-claim, but it breaks the PV-28 and residual (t) requirement that the clause cover exactly the relevant paths.
- **(iii) wording:** see R18-03.

**Impact:** caveat text claims more, and less, than was checked (P-21 / PV-28).

**Smallest correction:** state the C-text precondition in words: "each file that was text both before and after this commit where …". Define "non-text file" as "a file that was not text before or after this commit". Revise again once R18-01 is fixed.

### R18-03 — MEDIUM — Rule (iii)'s ⊥ convention makes every surviving addition or deletion a "mode change"

**Section:** §1.7.3 (iii); count-landing eligibility (Option (b)); Option A landing table; §4 `landing()`; CV1.

**Evidence:**
- "(iii) a mode change, mode(Post,p) ≠ mode(Pre,p), with mode(End,p) = mode(Post,p) (mode(⊥) := ⊥)".
- Option A: "C's surviving change at p includes a mode change → unverifiable".

**Counterexample:** C adds a new text file f with line L. The target independently edits nothing in f; the squash has r ≠ e only because of an unrelated target edit to f, for instance after an earlier target addition. mode(Pre,f) = ⊥ ≠ 100644 = mode(Post,f) = mode(End,f), so f "includes a mode change" by (iii) as literally written. Under Option A, f is never count-landing-eligible, so the result is K31. Under (b) × A, f is excluded from AS, so anchoring scope and CV7's "count-confirmed files" change.

A narrower implementation reading ("permission bits between two present entries") produces different Option A, AS and CV7 outcomes. With the literal reading, CV1's "each file whose mode change by this commit is unchanged" silently covers every file C added that still exists. Relevance in the interim rule loses nothing under either reading; the divergence is in owner-option outcomes.

**Impact:** an underspecified rule that changes the outcome for owner options UR-19 (b) and UR-21 A, and how much Option A is worth. The UR-21 cost text does not mention it.

**Smallest correction:** say which reading is intended. Either define a mode change as mode(Pre) ≠ ⊥ ≠ mode(Post) ∧ mode(Pre) ≠ mode(Post), or state explicitly that additions and deletions count and add that to the UR-21 Option A cost. Add one Option A fixture with a C-added file.

### R18-04 — MEDIUM — FX-C09c is not determinate under the argv first-occurrence rule

**Section:** §7.1 FX-C09c; §1.7.3 "Repeated calls"; L-22.

**Evidence:**
- "V_first's stage-1 `merge-base` call exceeds 60 s; V_second's stage-1 `merge-base` call exits 128. … (b), (b′): … no failure → MERGED".
- §1.7.3: "a call whose argv was already issued earlier … an argv-keyed [harness] injection therefore fails at the first occurrence of that argv".
- L-22: "X_v is always an endpoint in E, so the endpoint check has already made that merge base unique".

**Counterexample:**
1. In FX-K25c, V3 is chained with X_v = A1. A1 ∈ E, since A1 is reachable from br's tip via Bm and is not in T.
2. The endpoint check therefore issues `merge-base --all A1 T` before IA7. That is the same argv as V3's stage-1 Ht call.
3. V3 also has a second stage-1 call (Fk = `merge-base --all F0 A0`), so "V3's stage-1 merge-base call" is ambiguous.
4. If the harness keys V3's Ht call, the failure fires in the endpoint check in **every** UR-19 option. The result is then C09 or C10, depending on whether V3 sorts first or second. That contradicts both the (a) expectation (it holds only in one ordering) and the (b)/(b′) expectation "no failure → MERGED".

**Impact:** a priority-3 injection fixture is not determinate as written.

**Smallest correction:** name exact argvs. Inject only on V2's Fk (`merge-base --all M1 A0`) and V3's Fk (`merge-base --all F0 A0`). State that V3's Ht argv is answered from the endpoint check. Add a sentence to the repeated-calls rule saying pre-FINALIZE calls (IA1–IA6) belong to the same sequence.

### R18-05 — LOW — FX-C10e injects an argv that is never issued

**Evidence:** the fixture injects "`rev-list --count T --not <I.tip> -- f` … exits 128" on FX-K32a's history. In FX-K32a, "C removes L and also edits g", so paths(C) = {f, g}. DG issues `rev-list --count T --not I.tip -- f g`.

### R18-06 — LOW — Stale entry-based wording survives the R17-05 sweep

**Section:** FX-K31f, FX-K23ak, FX-K23ao; §11.23 step 4.

**Evidence:**
